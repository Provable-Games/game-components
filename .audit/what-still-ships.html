Removal audit · game-components

What Still Ships

Which modules are genuinely dead, which are simply unconsumed, and the one question that gates the largest deletion.

Against 9ad9a33 tag v2.0.0 Scope: in-repo + budokan

The distinction that reframes this

The obvious method — find modules nothing imports, delete them — gives the wrong answer here, and would have deleted working product.

game-components is a library. Its components exist to be embedded by game developers downstream, not called from within this repo. So "no in-repo consumer" is the normal state for a healthy module, not evidence of death.

The discriminator isn't consumers. It's whether anyone is still maintaining it.

A module with tests and a CI matrix entry is a shipped product waiting for its first embedder. A module with neither is an abandoned draft. One of these is worth keeping; the other never finished being written.

Applied to the three modules with no consumer anywhere, that separates cleanly — and only one of them is actually dead.

gpp is the one clear deletion

Guaranteed prize pool management. It arrived complete in a single commit and has not been touched since — no follow-up, no test pass, no CI wiring, no embedder.

  • Origin42fe1c2 — "feat: add GppComponent for guaranteed prize pool management" (#95)
  • Commits sinceNone. The module has never been modified.
  • Tests0 across all three files
  • CINot in pr-ci.yml, main-ci.yml, or codecov.yml
  • ConsumersNone found in-repo or in budokan (either branch)
  • Footprint681 lines across gpp_component, store, structs, plus interfaces/src/gpp.cairo

Worth noting it does compile — it's declared in lib.cairo, so scarb build covers it. It has simply never been tested by anything. That's a CI gap as much as a dead-code finding: if you keep it, it needs a matrix entry and tests; if the feature isn't happening, it should go.

This one is safe to delete now and doesn't depend on anything else in this document.

The registry cluster is one unit, not three

The original ask was "remove the registry". It can't be removed alone — it's load-bearing for two other modules, and they stand or fall together.

Blocked
embeddable_game_standard::registry
Serves token_legacy. Also still owns GameFeeInfo and FEE_DENOMINATOR, which the standard generation uses.
5,324 lines
Blocked
embeddable_game_standard::minigame
Legacy-only by design — asserts IMINIGAME_TOKEN_LEGACY_ID and calls register_game. A standard-token game embeds the token component directly.
7,576 lines
Blocked
embeddable_game_standard::token_legacy
Preserved deliberately for deployed denshokan. Carries seven extensions the standard token has none of: context, enumerable, minter, objectives, renderer, settings, skills.
26,384 lines

Pull registry out and the other two stop compiling. So the decision on the table isn't "delete registry" — it's "retire the legacy generation, ~39,300 lines".

No current consumer touches any of it. Budokan v2 removed the registry entirely — its five apparent references are all comments. SDM is standard-native. Inside this repo, the only thing keeping the cluster alive is the legacy generation itself.

The question that gates it

Is deployed denshokan still live, and does anything still need to build against it?

That isn't answerable from the code. token_legacy exists specifically to serve a deployment, and its interface id (IMINIGAME_TOKEN_LEGACY_ID) is frozen because a live contract registers it on chain. If the answer is no, all 39,300 lines go together. If the answer is yes, none of them do.

One coupling to break either way

GameFeeInfo, FEE_DENOMINATOR and DEFAULT_GAME_FEE_BPS live in the registry's interface — and the standard generation depends on all three:

  • Standard tokentoken/game_fee.cairo re-exports DEFAULT_GAME_FEE_BPS and FEE_DENOMINATOR straight from registry
  • Token componentminigame_token_component uses both for its initializer's fee validation
  • Metagamemetagame.cairo returns GameFeeInfo and divides by FEE_DENOMINATOR

These three symbols are generation-neutral — a fee denominator isn't a registry concept. Moving them to their own module is correct whether or not the registry ever goes, and it's a hard prerequisite for removing it. Everything else in the registry interface (IMinigameRegistry, GameMetadata, the v1.0 default_license) is genuinely registry-specific and stays.

Recommended order

Three steps, increasing in both size and required certainty:

  • NowDecouple the three fee symbols. Small, correct regardless, unblocks everything below.
  • NowDelete gpp — or wire it into CI with tests if the feature is still wanted. Independent of the rest.
  • GatedRetire the legacy cluster, once the denshokan question has an answer. Own PR, not folded into anything else.

Method and limits

Consumers were traced by symbol across packages/ excluding each module's own tree, and across budokan on both main and feat/budokan-v2-lite. Test counts are #[test] markers; CI membership is presence in the workflow matrices and codecov.yml. Line counts are total .cairo lines including tests.

Not examined: the utilities and economy packages, the presets package beyond confirming budokan doesn't consume it, and consumers outside this repo and budokan — notably SDM, which was checked only for the registry question. A module absent from this document has not been cleared; it has not been looked at.

Everything asserted here was verified against 9ad9a33 at the time of writing. The gpp and coupling findings are stable; consumer claims about budokan reflect its branches as of this commit and should be re-checked if that work moves.
